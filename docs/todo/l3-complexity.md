# L3 智能度的边界与方向

## 核心矛盾：没有反馈信号，复杂度 ≠ 更准

L3 的所有"更智能"路径都撞同一堵墙：**永远缺一个反馈信号**。没有反馈就没法验证"更复杂"到底是不是"更好"。

## 复杂度往哪加，都会撞墙

| 可能想加的复杂度 | 为什么不能变准 |
|-------------------|---------------|
| 更精细的阈值（短/中/长/超长多档） | 仍然是**输入特征猜难度**，多档只是多几个猜错的点 |
| 关键词分类器（"debug"/"refactor"→pro） | CC 整套 prompt 里什么词都有，关键词和真实难度的相关性是幻觉 |
| LLM 分类器（小模型先判难度再路由） | **每请求多一次 LLM 调用**——省下的 flash/pro 差价可能不够分类成本，还加延迟 |
| 历史学习（记住"上次类似请求走 flash 失败了"） | **永远不知道**走 flash 是否"失败"——没有质量 ground truth |

## 类比

像**没有考试答案却想优化学习策略**。可以把计划搞得很复杂（多档复习、间隔重复、分类训练），但没有对错反馈，不知道哪种有效，复杂度只让人**感觉**在进步。

## 真正能变准的唯一路径：拿到反馈信号

复杂度该加在**反馈环**，不是**判断逻辑**。可能的反馈信号：

| 信号 | 来源 | 可靠度 | 实现难度 |
|------|------|--------|---------|
| `stop_reason: max_tokens`（flash 被截断） | SSE message_stop 事件 | 高（客观事实） | 中（要从流里采样，不能破坏透传） |
| CC 接 flash 后立即重试 | CC 行为模式（同请求短时间内再来） | 中（可能是正常多轮） | 高（要跨请求关联） |
| CC 接 flash 后手动切 opus 重做 | CC 行为模式 | 高（强隐式反馈） | 高（同上） |
| 用户手动 `/model` 切换 | CC 命令 | 高 | 不可得（awerouter 看不到） |

**`stop_reason: max_tokens` 是当前唯一能诚实挖到的质量代理**——这也是 `l3-threshold.md` 里 calibrate 加截断率分桶排第一的原因。

## 结论

- **L3 判断逻辑本身已到合理上限**：token 启发式 + 含图判断，够用了
- **不在 L3 判断上加复杂度**：自适应阈值、关键词分类器、LLM 分类器都是黑洞
- **复杂度加在反馈收集上**：先做 SSE 截断率采样（calibrate 的结果维度），这是从"猜"变成"知道"的第一步
- **L3 的价值不在"准"，在"自动"**：虽然有误判，但这个生态位（主循环自动 flash/pro 分流）目前没人在填。"有缺陷的自动路由" > "没有自动路由"

## 和其他工具的边界

| 工具 | 做什么 | 和 awerouter L3 的关系 |
|------|--------|----------------------|
| opencode subagent @-dispatch | 用户手动委派任务给不同 agent | **不冲突**——不做自动路由，需要人 @ |
| CC /model 切换 | 用户手动选档位 | **不冲突**——是 L2 信号源，不是 L3 竞品 |
| awerouter L3 | 按请求特征自动分流主循环 | **唯一填这个生态位的东西** |

awerouter L3 的护城河不是"判断准"（它不准），是"自动 + 客户端无关 + 零分类成本"。没有其他工具在这个位置。
