# L3 阈值调优路线

## 背景

`longContextThreshold` 是 L3 难度评分层的唯一旋钮：token 超阈值或含图 → pro，否则 → flash。
当前靠人拍脑袋或 `calibrate` 看分布定。

## 明确放弃：自适应阈值

**结论：不做。**

理由（详见下文"为什么放弃"）：L3 这层没有可靠的质量反馈信号，自适应没有可优化的目标。
唯一能自动优化的是成本，而那会把阈值推到无穷大 = 全走 flash = 废掉 L3，且流量漂移导致
同一类请求今天 flash 明天 pro，不可解释、不可复现。

## 要做的三件事（按优先级）

### 1. 给 calibrate 加结果维度（真信息缺口，先做）

**问题**：现在 `calibrate` 只画 token 分布，但人最想知道的是"flash 到底在哪开始崩"。

**做法**：按 token 分桶统计每桶的——
- 5xx / error 率
- `stop_reason: max_tokens`（截断）率 —— 这是唯一能从 SSE 里**诚实挖出来**的质量代理

**输出变成**：
> 500–1000 token 段，flash 截断率 12% → 建议阈值降到 500

这是有**证据**的决策，不是猜。

**成本**：低，纯增量。
**前置**：需要从 SSE 响应里提取 `stop_reason`（目前透传不解析；要在不破坏流式的前提下
采样 message_stop 事件）。

### 2. 成本感知建议

**做法**：`calibrate` 加一列 —— 每个候选阈值下的估算 flash/pro 成本比
（provider 单价 × token）。

**效果**：让"省钱 vs 防崩"这个权衡**可见、可量化**，人拍板。

**前置**：需要 provider 单价数据（可能要加到 providers.json 或单独定价文件）。

### 3. Provider 健康自适应（独立 feature，不是改阈值）

**支持做** —— 但它**不是改 `longContextThreshold`**，而是改**默认目的地**：

- 当 flash provider 近 N 分钟 5xx 率超 X%，L3 的 default 暂时偏 pro
- 冷却后恢复
- 这是**健康自适应**，不是**难度自适应**：目标明确、信号可靠、可解释
- 现有的 pre-stream fallback 已经处理了急性单次失败，这是它的"软降级"版

---

## 为什么放弃自适应阈值

L3 这层能观测到的信号：

| 信号 | 能不能当"路由对了"的证据 |
|------|------------------------|
| status code (200/429/5xx) | ✗ 只反映 provider 健康，不反映难度 |
| 延迟 | ✗ 和 provider 负载强相关，和难度弱相关 |
| token 数 | ✗ 这是**输入特征**，不是**结果** |
| 响应质量 | ✗ **没有** —— 我们没有 ground truth |

**没有质量信号 = 自适应没有优化目标。** 唯一能自动优化的是成本，那它会把阈值推到无穷大
= 全走 flash = 直接把 L3 废掉（Goodhart 定律）。或者追着流量分布漂移（CC 流量是突发性的），
9 点的"长"到 3 点变"正常"，同一类请求今天 flash 明天 pro，不可解释、不可复现。

而且 `calibrate` 已经解决了**信息**问题。剩下的本质是一个**人的成本/质量权衡**，
这种决策不该让机器猜。

---

## 建议执行顺序

1. **先做 #1（结果维度）** —— 填补 `calibrate` 的真实缺口、低成本、纯增量。
2. **#2 看你有没有 provider 单价数据**。
3. **#3 是独立 feature**，按需做。
